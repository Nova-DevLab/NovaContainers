# list의 연속 재구성

`optimize()`는 논리적 순서를 유지하면서 살아 있는 원소를 하나의 메인 배열에 재구성합니다. 정렬하는 함수는 아닙니다. 추가 작업은 별도 블록에서 계속할 수 있으며 다시 `optimize()`하여 합칩니다. 메모리 정리도 이 함수로 통합하며 list의 `shrink_to_fit()`은 제공하지 않습니다.

```cpp
nova::list<int> values;
for (int i = 0; i < 100000; ++i) values.push_back(i);
values.optimize();

for (const int value : values) {
	Consume(value);
}
for (const int value : values.contiguous_view()) {
	Consume(value);
}

values.push_front(-1);
values.push_back(100000);
values.optimize();
```

## 저장 구조

- 디렉터리 엔트리는 원소 포인터와 개별 소유 여부를 저장합니다. 메인 배열의 조각은 비소유 엔트리이며 추가 블록만 개별 할당을 소유합니다.
- Optimize는 현재 원소 수를 블록 단위로 반올림한 크기의 메인 배열을 사용자 allocator로 한 번 할당합니다. 디렉터리는 이 배열의 조각을 가리킵니다.
- 기존 메인 배열과 추가 블록은 새 배열 구성에 성공한 뒤 반환합니다. 재구성 중에는 기존 저장소와 새 저장소가 동시에 존재합니다.
- 최적화 직후 앞쪽 여유 공간은 없고 뒤쪽에는 마지막 블록의 미사용 슬롯이 있을 수 있습니다. 뒤 여유 슬롯이 있으면 연속 상태로 추가할 수 있습니다.
- 메인 배열 바깥에 양끝 추가가 필요하면 별도 블록을 할당합니다. 이때 기존 원소를 이동하지 않습니다.
- 삭제 후에도 살아 있는 원소가 메인 배열에 남아 있으면 메인 배열의 모든 디렉터리 조각을 유지합니다. 삭제한 영역은 앞뒤 여유로 재사용하며 `capacity()`에 포함합니다. 메인 배열을 부분 반환하지는 않습니다. 원소가 전부 외부 블록으로 넘어가면 사용하지 않는 메인 배열 전체를 반환합니다. 빈 목록과 `clear()`는 용량을 유지하고, `optimize()`는 남은 저장소를 반환합니다.
- `capacity() == size() + front_capacity() + back_capacity()`이며, 현재 보유한 원소 저장소의 총 슬롯 수입니다. 디렉터리와 allocator 자체의 관리 메모리는 포함하지 않습니다.

## 연속 상태와 순회

- `is_contiguous()`는 빈 목록 또는 모든 원소가 하나의 물리적 할당 안에 순서대로 놓인 상태에서 true입니다. 일반 단일 블록도 true입니다.
- 연속 상태여도 큰 메인 배열이나 예약 블록이 남아 있으면 재구성합니다. 메인 배열 시작점에 원소가 있고 배열 크기가 현재 원소 수를 블록 단위로 반올림한 크기이며 예약 블록과 디렉터리 여유가 없는 경우에만 재구성을 생략합니다. 빈 목록의 `optimize()`는 남은 저장소를 모두 반환합니다.
- 연속 상태의 일반 iterator는 node=nullptr 모드로 원소 포인터를 이동합니다. 블록형 상태에서는 기존 블록 경계 처리를 사용합니다. 고정 모드 플래그를 포함한 iterator 크기는 x64에서 24바이트입니다. 일반 range-for의 자동 벡터화와 속도 개선을 보장하지 않습니다.
- `operator[]`도 연속 상태에서는 메인 원소 포인터로 직접 접근합니다.
- `contiguous_view()`는 `std::span<T>` 또는 `std::span<const T>`를 반환합니다. 비연속 상태에서는 `std::logic_error`를 던집니다. 임시 컨테이너에는 호출할 수 없습니다.
- `blocks()`는 연속 상태에서 전체 살아 있는 원소를 하나의 span으로 반환합니다. 비연속 상태에서는 블록별 span을 반환합니다.
- 하나의 span과 일반 iterator의 실제 성능은 별도로 측정합니다. 일반 iterator의 타입은 항상 random-access이며 contiguous iterator로 선언하지 않습니다.

## 수명과 예외

- 실제 재구성은 모든 원소 주소, iterator와 기존 span을 무효화합니다. 최소 저장 상태에서의 no-op은 기존 원소를 이동하지 않습니다. 연속 상태만으로 주소 유지를 판단하지 않습니다.
- 양끝 추가는 기존 원소 주소를 유지합니다. 다만 추가·삭제로 iterator 모드가 바뀔 수 있으므로 구조 변경 후에는 iterator를 다시 얻습니다.
- span은 생성 당시의 길이를 갖습니다. 이후 추가된 원소를 자동으로 포함하지 않으며, 재구성 또는 해당 원소 삭제 후에는 재사용하지 않습니다.
- allocator 복사·이동·교환 규칙은 기존과 동일합니다. 개별 블록과 메인 할당은 각각의 정확한 할당 크기로 한 번씩 반환합니다.
- 재구성 시 `std::move_if_noexcept`를 사용합니다. 복사 가능한 타입에서 복사를 선택했다가 실패하면 기존 값·순서·주소를 유지합니다. move-only 타입의 이동 중 예외는 basic guarantee이며 기존 값 일부가 이동된 상태일 수 있습니다.
- 복사는 값의 순서를 보존하지만 최적화된 저장 상태까지 보존한다고 보장하지 않습니다. 이동과 교환은 저장소와 상태를 함께 이관합니다.

## 검증과 측정

`nova_containers_list_optimize_tests`가 블록 경계·혼합 상태·반복 최적화·주소 안정성·기존 알고리즘·allocator·예외를 검증합니다.

`nova_containers_list_optimize_benchmark [count] [iterations] [order] [sort]`는 분리 저장, 최적화 후, 다시 추가한 혼합 상태, 재최적화 후를 같은 함수에서 비교합니다. vector/deque와 일반 range-for, 인덱스 for, span, 랜덤 조회를 구분하고 Optimize 비용도 별도로 기록합니다.

### 2026-11-04 최종 단일 실행

Release 관련 테스트 2/2 통과. 이번 테스트 보완은 mutable span 변경의 원본 반영, 반복자 const 변환·덧셈·뺄셈, 혼합 상태에서 연속 뷰 거부, 반복 재최적화를 검증합니다.

실행 명령: `nova_containers_list_optimize_benchmark 100000 30 0 1`. 실행은 한 번이며, 내부에서 읽기는 표본별 30회, 정렬과 재구성은 표본별 1회씩 측정한 5개 표본의 중앙값입니다. 모든 값은 한 작업당 시간입니다. 준비·복사 시간은 정렬 및 Optimize 시간에서 제외합니다.

| 자료형 | 작업 | 분리 블록 | Optimize 후 |
|---|---|---:|---:|
| uint64_t | 일반 range-for | 35.15 us | 37.36 us |
| uint64_t | 인덱스 for | 77.49 us | 44.86 us |
| uint64_t | 정렬 | 7.942 ms | 7.130 ms |
| 64바이트 레코드 | 일반 range-for | 130.72 us | 122.62 us |
| 64바이트 레코드 | 인덱스 for | 131.35 us | 118.44 us |
| 64바이트 레코드 | 정렬 | 8.495 ms | 8.146 ms |

uint64_t 인덱스 for는 약 42.1%, 정렬은 약 10.2% 시간이 감소했습니다. 일반 range-for는 약 6.3% 증가하여 개선되지 않았습니다. 64바이트 레코드 정렬의 감소는 이번 실행에서 약 4.1%이며, 이전 실험의 10~13% 수치를 모든 타입에 적용하지 않습니다.

최적화 후 uint64_t 연속 뷰는 7.06 us, 같은 상태의 vector 연속 뷰는 7.60 us였습니다. 이 합산 작업에서 비슷한 수준이며 다른 작업의 성능을 보장하지 않습니다. Optimize 자체 비용은 uint64_t 0.254 ms, 64바이트 레코드 1.777 ms입니다. 실제 재구성은 O(N)입니다. 위 측정 당시에는 이미 연속인 비어 있지 않은 목록이 O(1) no-op이었으며, 아래 메모리 정리 변경 후에는 최소 저장 상태인 경우에만 no-op입니다.

환경: Intel i7-1165G7, MSVC 19.51, x64 Release, C++20, AVX2. 논리 CPU 1개(affinity mask 2), BelowNormal, 빌드 작업 1개. 측정 순서 0은 읽기 순서 설정이며 메모리 할당 순서를 뒤집은 실험은 아닙니다. 단일 실행 결과로 시스템 부하에 따른 편차가 있습니다.

## 2026-11-04 메모리 정리 통합

list의 `shrink_to_fit()`을 제거하고 `optimize()`가 연속 재구성과 메모리 축소를 함께 수행하도록 변경했습니다. 기존에는 `is_contiguous()`만 보고 종료했으므로 큰 메인 배열에서 양끝 원소를 삭제해도 보유량이 줄지 않았습니다. 이제 메인 배열 크기·시작 위치, 예약 블록과 디렉터리 크기까지 최소 저장 상태인지 확인합니다. 기존 `shrink_to_fit()` 호출은 `optimize()`로 변경해야 하며 실제 재구성 후 원소 주소·iterator·span을 다시 얻어야 합니다.

같은 날 같은 Release 하니스에서 사용자 allocator의 실제 할당·반환 크기를 추적했습니다. `int`, BlockBytes=16, 블록당 4개 원소를 사용하고 4,096개를 최적화한 뒤 앞 1,000개와 뒤 원소를 삭제해 5개를 남기는 동일 시나리오입니다.

| 구현 | 삭제 직후 원소 저장소 | optimize 후 원소 저장소 |
|---|---:|---:|
| 변경 전 | 16,384바이트 | 16,384바이트 |
| 변경 후 | 16,384바이트 | 32바이트 |

변경 후 5개 원소는 8슬롯(32바이트)을 보유합니다. 블록 반올림 때문에 한 블록 미만의 여유는 남습니다. 위 수치는 원소 할당량이며 디렉터리, allocator 내부 오버헤드, 프로세스 working set은 포함하지 않습니다. OS에 즉시 반환되는 양과 CPU 시간은 미검증입니다. 재구성 중에는 기존 저장소와 새 저장소가 동시에 존재하므로 순간 최대 메모리가 최종 보유량보다 큽니다. 요소·iterator 레이아웃은 변경하지 않았습니다.

검증 명령은 `.\run_list_harness.ps1`입니다. Release 빌드와 리스트 CTest 2/2를 통과했습니다. BelowNormal, 논리 CPU 1개, 빌드·테스트 병렬 작업 1개와 MSVC 코드 생성·링크 스레드 제한을 적용했습니다. 회귀 테스트는 보유 메모리 감소, 예약 블록 반환, 사용하지 않는 메인 배열 반환, 빈 목록 해제, 최소 상태 반복 호출의 재할당 생략과 축소 중 할당·복사 예외 보장을 검사합니다.
