# list 청크형 범위 삽입 A/B 검증

검토일: 2026-11-04.

이 문서는 임시 청크 버퍼를 사용하던 중간 단계의 실험 기록입니다. 아래 vector 복원 권장은 이후 직접 예약 삽입으로 대체했습니다. 현재 구현의 채택 근거는 [직접 삽입 검증](list_direct_validation.md)입니다.

## 판단

길이를 미리 아는 큰 범위까지 청크형 버퍼로 바꾼 현재 구현 전체를 성능 개선으로 채택하는 것은 권장하지 않습니다. 길이가 알려진 범위는 기존 vector 사전 예약 경로를 유지하고, 단일 패스 입력에 청크 전환을 적용하는 방향을 권장합니다. 이번 작업에서는 라이브러리 구현을 추가로 변경하지 않았습니다.

확인함: 10만 개의 길이 있는 범위 삽입은 네 타입, 앞/중간/뒤, 두 초기 측정 순서의 24개 중앙값 모두 시간이 증가했습니다(+2.0~66.1%). 이 중 작은 차이는 대조군 편차와 구분하기 어렵지만, uint64_t와 record64 뒤 삽입의 증가 폭은 두 실행에서 반복됐습니다. 최대 요청량도 뒤 삽입에서 0.07~0.23% 증가했습니다. 원소당 임시 저장 크기는 거의 같은 상태에서 블록 반올림, 디렉터리 및 다수의 블록 할당이 추가됩니다. 큰 단일 원소 배열 할당을 피한다는 특성은 있지만, 이번 조건의 총 요청 메모리는 줄지 않았습니다.

확인함: 10만 개 단일 패스 입력은 뒤 삽입 최고 요청량이 3.60~11.11% 감소했고 네 타입의 뒤 삽입 시간도 두 실행 모두 감소했습니다. 앞/중간/뒤 전체 24개 시간 중앙값 중 23개는 감소했지만, uint64_t 앞 삽입의 첫 실행은 +11.1%였습니다. 모든 단일 패스 입력에서 성능 무저하가 확인됐다고 주장하지 않습니다.

## 메모리 결과

아래는 같은 10만 개 뒤 삽입의 작업 중 최대 동시 할당 요청량입니다. 입력 vector, 기존 및 추가 원소 블록, 임시 버퍼, 디렉터리와 문자열의 힙 저장소를 포함합니다. allocator 내부 관리 정보, 추적 헤더와 프로세스 working set은 제외합니다. 메모리는 조건당 한 번 측정했으며 CSV의 9개 시간 표본에 반복 기록된 메모리 열을 독립된 메모리 측정 9회로 해석하지 않습니다.

128개 조건의 길이 있는 뒤 삽입은 네 타입 모두 요청량과 작업 할당 횟수가 동일했습니다. 시간은 코드 경로와 표본 편차의 영향을 받아 uint64_t 뒤 삽입 +17.6%/+23.2%, record64 +4.8%/+6.1%, 짧은 string +9.4%/+10.0%, 긴 string -5.1%/+5.8%였습니다. 작은 원소 작업은 수십~수백 ns 차이에도 비율이 커지므로 모든 수치를 일정한 회귀율로 일반화하지 않습니다.

128개 단일 패스 뒤 삽입은 최고 요청량이 타입에 따라 0.61~6.90% 감소했습니다. 시간은 uint64_t에서 -6.3%/+0.6%로 고정 개선을 확정하기 어렵고, 나머지 세 타입은 두 실행 모두 감소했습니다.

## 조건과 한계

- Intel Core i7-1165G7, 논리 프로세서 8개 중 하나만 사용(affinity=1), BelowNormal. 실제 cl/MSBuild 및 벤치마크 프로세스의 제한 적용을 확인했습니다.
- MSVC 19.51, x64 Release, C++20, AVX2. 빌드 작업 하나, /maxcpucount:1, /p:CL_MPCount=1, /cgthreads1, /CGTHREADS:1.
- 원소는 uint64_t(8B), record64(64B), MSVC string 객체(32B, 문자열 길이 6 또는 96자), BlockBytes=16384입니다. 양방향 큐 대조군만 BlockBytes=64입니다.
- 분리 저장 상태에서 측정했습니다. 128개 및 10만 개만 측정했으며, 다른 크기/플랫폼/allocator/연속 상태의 결과로 일반화하지 않습니다.
- 이전 헤더는 메인 배열 용량 재사용 수정을 유지하고, 직전 allocator max_size 및 범위 버퍼 변경만 되돌려 nova_baseline 네임스페이스로 격리했습니다. 표준 allocator를 사용하므로 작은 allocator 한도 지원의 성능은 측정하지 않았습니다.
- 시간은 전역 할당 추적 래퍼를 제거한 native 힙 실행 4회(두 건수와 두 초기 측정 순서)로 평가했습니다. 128개는 표본당 100회, 10만 개는 3회입니다. 각 실행에서 두 경로를 워밍업한 뒤 9개 표본의 A/B 순서를 교대했습니다. 최초 할당 순서 무작위화나 하드웨어 카운터 측정은 하지 않았습니다.
- 단일 패스 입력은 준비된 vector를 뺄셈 없는 input iterator로 노출합니다. 스트림 파싱과 I/O 비용은 포함하지 않습니다. 준비/체크섬 확인/파괴는 삽입 시간에서 제외합니다.
- 순회/정렬/개수 삽입/큐 대조군도 함께 측정했습니다. 10만 개 대조군의 시간 변화에는 약 -18.5~+13.7%가 섞였습니다. 이를 이번 변경의 개선으로 계산하지 않으며, 작은 차이의 원인을 확정하지 않습니다.
- Release 벤치마크 빌드와 8개 A/B 실행이 모두 성공했습니다. 메모리 추적, 워밍업, 모든 시간 표본의 A/B 체크섬이 일치했고 추적 요청 바이트의 해제 검사가 통과했습니다. 기존 CTest는 이번 성능 검증에서 재실행하지 않았습니다.
- list<uint64_t> 88바이트, iterator 24바이트입니다. 이번 작업에서 라이브러리 헤더는 변경하지 않았고 측정 전후 SHA-256이 일치합니다.
