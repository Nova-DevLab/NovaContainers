# list 메모리 최적화 후보 검토

후속 구현에서는 후보 1, 2를 적용하고 후보 3은 성능 유지 근거 부족으로 제외했습니다. 실제 측정과 최종 검증은 [구현 결과](list_memory_optimization.md)를 참고합니다. 아래 내용은 구현 전 검토 기록입니다.

검토일: 2026-11-04. 대상은 현재 include/NovaContainers/list.hpp입니다. 라이브러리 소스는 변경하지 않았습니다. 아래 항목은 구현 후보이며 성능 개선 또는 무저하가 실측으로 확인된 변경이 아닙니다.

## 결론과 우선순위

| 순위 | 후보 | 예상 절감 대상 | 판단 |
|---|---|---|---|
| 1 | 개수 지정 insert의 원소 임시 배열 제거 | count * sizeof(T)의 임시 원소 저장소 | 먼저 독립적으로 구현하고 검증할 후보 |
| 2 | 길이를 O(1)에 구할 수 있는 범위 insert의 임시 버퍼 reserve | vector 성장 중 여유 슬롯과 구/신 버퍼의 동시 보유 | 자기 범위 삽입 버퍼는 유지하며 검토 |
| 3 | 동일 크기 디렉터리 재배치를 제자리 이동으로 변경 | 재배치 중 디렉터리 하나 분량의 추가 할당 | 고정 길이 큐에서 우선 검토 |
| 보류 | 디렉터리 소유 플래그 분리 | 엔트리의 정렬 패딩 | 기본 블록에서는 효과가 작고 접근 비용 검증 필요 |

세 후보 모두 원소 블록 크기와 일반 iterator 레이아웃을 유지할 수 있습니다. 그래도 실제 코드 변경 후 같은 날 A/B 검증을 통과해야 채택할 수 있습니다.

## 1. 개수 지정 insert의 임시 배열 제거

확인함: insert(position, count, value)는 std::vector<T, Alloc> values(count, value, allocator_)를 만든 뒤 insert_buffered로 전달합니다. insert_buffered는 이 배열의 원소를 양끝에 이동 생성하고 std::rotate로 삽입 위치를 맞춥니다. 따라서 원소 배열 두 곳이 동시에 필요합니다. 임시 배열은 함수가 끝날 때까지 살아 있습니다.

후보: 삽입 방향과 개수를 먼저 결정하고 reserve_front/back 후 value를 해당 끝에 count번 직접 복사 생성합니다. 생성에 모두 성공한 뒤 현재와 동일하게 rotate합니다. 실패 시 이번에 생성한 원소만 pop하여 되돌립니다. 기존 구현이 보장하는 양끝 확장 시 원소 주소 유지 때문에 value가 같은 list의 원소여도 추가 생성 동안 참조가 유지됩니다. 앞쪽 삽입도 동일 값의 반복이므로 역순 임시 배열이 필요하지 않습니다.

계산: 100만 개 삽입에서 sizeof(T)=8이면 임시 원소 저장소 8,000,000바이트, sizeof(T)=64이면 64,000,000바이트를 제거하는 후보입니다. vector의 추가 여유 용량, allocator 관리 정보, T가 별도로 소유한 힙 메모리는 이 계산에 포함하지 않았습니다. 최종 원소 저장소는 그대로 필요합니다. 이는 저장소 계산이며 working set 실측이 아닙니다.

기능 조건: count=0에서 생성하지 않기, 길이 초과 검사 유지, 내부 value 참조 지원, 양쪽 방향의 복사 실패 롤백, rotate 실패 시 기존 basic guarantee, 사용자 allocator construct/destroy 및 반환 크기를 유지해야 합니다. 현재의 count회 복사와 count회 이동을 count회 직접 복사로 바꾸므로 불필요한 이동과 버퍼 할당을 줄일 가능성이 있습니다. 실제 CPU 시간은 미검증입니다.

## 2. 길이가 알려진 범위 삽입의 버퍼 사전 예약

확인함: 범위 insert는 빈 std::vector<T, Alloc>에 emplace_back을 반복합니다. 초기 reserve가 없습니다. 반면 범위 생성자는 forward iterator일 때 이미 reserve_back을 사용합니다. 이 생성자 개선은 신규 후보로 중복 제안하지 않습니다.

후보: std::sized_sentinel_for<InputIt, InputIt>처럼 거리 계산이 O(1)인 경우에만 남은 max_size와 버퍼 max_size를 검사하고 values.reserve(count)를 수행합니다. input iterator는 기존 단일 순회를 유지합니다. 거리를 구하려고 일반 forward iterator를 한 번 더 순회하는 변경은 성능 무저하 조건에 맞지 않을 수 있으므로 이 후보에서 제외합니다.

자기 범위 삽입과 이동 iterator를 포함한 원본 범위의 수명 때문에 범위 버퍼 자체는 유지합니다. vector의 기하 증가에 따른 반복 할당, 원소 재이동 및 재할당 순간 구/신 버퍼의 중복 보유를 줄이는 방향입니다. 정확한 절감량은 현재 STL의 성장 정책, count, T, allocator에 따라 달라집니다. 고정 절감률을 제시하지 않습니다. 단일 대형 연속 할당이 필요하다는 문제는 여전히 남습니다.

기능 조건: 자기 범위 삽입, 단일 패스 입력, 빈 범위, move-only 원소의 이동 범위, 길이 초과, 할당/복사 예외와 기존 원소 보존을 검증해야 합니다. reserve는 미사용 원소를 생성하거나 초기화하지 않습니다.

## 3. 같은 크기의 디렉터리 재배치에서 추가 할당 제거

확인함: rebuild_directory는 needed <= directory_.size()/2이면 기존 length를 유지하지만, 이 경우에도 std::vector<block_entry> replacement(length)를 새로 할당합니다. 고정 길이 큐에서 디렉터리가 계속 커지는 문제는 이미 방지되어 있지만 재배치 할당은 남아 있습니다.

후보: length가 기존 directory_.size()와 같으면 살아 있는 엔트리 구간을 겹침 방향에 맞춰 제자리 이동하고, 이동 후 비활성 구간만 비웁니다. first_, allocated_begin_, allocated_end_를 새 위치에 맞춥니다. 원소 저장소는 이동하지 않습니다. 크기가 달라지는 경우에는 기존 경로를 유지합니다.

메모리 계산: x64에서 포인터 크기/정렬 8, bool 크기 1이라는 ABI 조건을 적용하면 block_entry는 패딩 포함 16바이트로 계산됩니다. 이 조건에서 length=1024인 재배치의 임시 디렉터리 저장소는 16,384바이트입니다. 제자리 이동은 이 추가 저장소를 없애는 후보이며 평상시 디렉터리 보유량은 줄이지 않습니다. 실제 sizeof 및 vector.capacity는 이번 실행에서 측정하지 못했습니다.

기능 조건: 겹치는 구간의 양방향 이동, 빈 상태, main의 비소유 엔트리와 추가 블록의 소유 엔트리 혼합, 마지막 경계용 빈 엔트리, 실패 후 재사용을 검증합니다. 옮긴 엔트리를 다시 지워 소유권을 잃거나 두 번 반환하지 않도록 해야 합니다. 기존 계약처럼 reserve/구조 변경 후 iterator는 다시 얻습니다. 단순히 std::rotate로 전체 디렉터리를 돌리면 이동량이 증가할 수 있으므로 실제 할당된 구간만 이동하는 안을 우선합니다.

## 보류하거나 제외한 변경

- 소유 플래그: block_entry의 포인터와 bool을 분리하면 패딩 절감 여지가 있습니다. 위 ABI 계산에서 포인터 전용 엔트리는 8바이트지만 소유 정보를 저장할 별도 메모리와 접근 비용이 추가됩니다. 기본 16KiB 블록에서 sizeof(T)=8이면 블록당 2048개이므로 100만 개의 최소 원소 블록 수는 489개입니다. 엔트리당 8바이트 절감은 최소 엔트리 기준 3912바이트에 불과합니다. 실제 디렉터리 여유 슬롯에 따른 차이는 별도입니다. T가 크거나 BlockBytes가 작아 블록 수가 많을 때 재검토합니다. main/추가 블록 소유권과 연속성 판정은 유지해야 합니다.
- 포인터 비트 태깅: T=char와 사용자 allocator의 최소 정렬을 일률적으로 가정할 수 없으므로 일반 해법으로 권장하지 않습니다.
- iterator의 linear_ 제거: 현재 모드 플래그는 순회 코드 생성과 관계가 있습니다. 이전 순회 검토에서 여러 레이아웃 후보의 회귀가 기록되어 있으므로 단순 필드 중복만으로 제거하지 않습니다.
- 기본 BlockBytes 축소: 작은 list 하나가 int 한 개만 담아도 원소 블록에 16,384바이트를 요청하는 것은 현재 수식으로 확인됩니다. 다수의 작은 list에서는 효과가 클 수 있지만 블록 증가, 할당 횟수, 순회 경계 처리와 랜덤 접근 비용이 늘 수 있습니다. 기본값 변경은 보류하고 실제 작은 목록 워크로드에서 기존 BlockBytes 템플릿 인자 조정을 별도 A/B 측정합니다.
- 자동 clear/마지막 pop 메모리 반환: 현재 저장소를 보유하여 재사용합니다. 무조건 반환하면 반복 채우기의 할당 비용이 늘 수 있어 제외합니다. 명시적인 빈 목록 optimize()는 이미 전체 저장소를 반환합니다.
- optimize의 main 배열 축소: 과도한 main과 예약 블록을 반환하는 동작과 회귀 테스트가 이미 있습니다. 신규 후보로 제안하지 않습니다. 일반적인 optimize는 재구성 중 기존 저장소와 새 저장소를 함께 보유하므로 항상 순간 최대 메모리를 줄이는 방법은 아닙니다.

## 채택 전 검증

후보 하나씩 분리하여 구현합니다. 기본 원소를 int/uint64_t/64바이트 레코드/짧고 긴 std::string으로 구분하고, 내부 참조 삽입과 사용자 allocator, 예외 원소도 검사합니다. 큰 단일 할당을 피해야 하는 워크로드는 별도 조건으로 둡니다.

Release 빌드와 기존 list 테스트 2개를 통과한 뒤, 해당 작업의 A/B에서 메모리 최고 보유량과 작업 시간을 함께 기록합니다. 원소 allocator만 추적하면 std::allocator를 쓰는 directory_ 메모리가 누락되므로 디렉터리 포함 할당 추적이 필요합니다. 문자열 자체의 힙 메모리와 allocator 내부 오버헤드 포함 여부도 명시합니다.

삽입 후보는 앞/중간/뒤, 작은 count와 대량 count를 나누고, 디렉터리 후보는 고정 길이 큐의 반복 재배치 및 일반 양끝 추가를 측정합니다. 일반 정/역방향 순회, 인덱스 접근, 정렬과 optimize 전후도 회귀 대조군으로 둡니다. A/B 순서를 교차하고 반복 표본의 편차를 확인합니다. 허용된 성능 저하 폭은 정해지지 않았으므로 측정 잡음 범위를 넘는 회귀가 반복되면 채택하지 않습니다.

빌드/측정은 논리 CPU 1개, BelowNormal, 병렬 작업 1개 및 MSVC 코드 생성/링크 제한을 적용합니다.

## 이번 검토의 검증 범위

현재 구현, 기존 설계/측정 문서 및 관련 테스트를 정적으로 확인했고 위 저장소 산식을 계산했습니다. 셸 프로세스 시작의 접근 거부와 대체 실행의 EPERM으로 새 Release 빌드, 테스트, sizeof 측정 및 A/B 실행은 하지 못했습니다. 기존 문서의 통과 기록을 이번 실행의 통과 결과로 취급하지 않습니다. 변경은 이 문서 추가뿐이며 라이브러리 기능과 레이아웃은 변경하지 않았습니다.
